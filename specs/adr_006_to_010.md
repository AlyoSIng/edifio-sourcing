## ADR-006 — Repo dédié `AlyoSIng/edifio-sourcing` (pas de monorepo)

**Statut** : Acté Board 2026-05-10
**Date** : 2026-05-10

### Contexte
La Phase 0 actait un monorepo `edifio-platform` à étendre. Premier contact réel : (1) le repo `edifio-platform` n'existait pas, (2) le repo `edifio-site` existant est un Next.js standalone non-monorepo qui sert le site marketing edifio.fr en production, (3) la complexité de migrer `edifio-site` dans un monorepo dépasse le scope MVP.

### Décision
**Abandon du monorepo Turborepo. Repo dédié `AlyoSIng/edifio-sourcing` (Next.js standalone classique)** pour edifio Sourcing. Aucun lien avec `edifio-site` qui reste en repo distinct.

### Conséquences
- ✅ Démarrage rapide, pas de migration risquée d'un site en prod
- ✅ Pas de packages `@edifio/*` factorisés au MVP — un seul `package.json`, un seul build
- ⚠️ Si Phase 2 voit naître plusieurs nouveaux modules edifio internes, une factorisation `@edifio/ui` redeviendra pertinente. À ce moment, on évaluera le monorepo (Turborepo) ou la factorisation par publication NPM privé.
- ⚠️ Risque léger de divergence visuelle entre edifio Sourcing et `edifio-site` → mitigation par `design/tokens.json` partagé comme source de vérité.

### Alternatives rejetées
- **Monorepo Turborepo from scratch** : effort de setup > 1 semaine, pas justifié pour un seul produit
- **Intégrer edifio Sourcing dans `edifio-site`** : risque de casser un site marketing en production, scope MVP explose

## ADR-007 — Auth email + mot de passe (au lieu de magic-link)

**Statut** : Acté Board 2026-05-10
**Date** : 2026-05-10

### Contexte
Le brief initial Phase 0 + Gate 5 actait un flow magic-link Supabase. Le test réel sur preview Vercel a révélé trois problèmes :
1. Le scanner email d'entreprise AlyoS pré-clique automatiquement le lien magic-link et consomme le token avant que l'utilisateur n'ait le temps de cliquer
2. edifio Suivi (autre module de la fratrie) utilise un flow email + password durable — incohérence UX si edifio Sourcing utilise magic-link
3. L'IT AlyoS ne va pas whitelister Supabase pour bypasser le scanner

### Décision
**Flow standard email + mot de passe**. Workflow :
1. Admin AlyoS crée le compte d'un collaborateur via `/sourcing/admin/users` (email + nom + rôle)
2. Système génère un mot de passe provisoire 16 caractères URL-safe
3. Email Resend envoyé au futur user avec mot de passe + lien direct vers `/login`
4. À la première connexion, force-redirect vers `/reset-password` (must_change_password=true)
5. Le user choisit son mot de passe définitif conforme aux règles
6. Sessions JWT durables Supabase Auth (30 jours refresh token rotation)

### Conséquences
- ✅ Robuste face aux scanners email entreprise
- ✅ Cohérence UX avec edifio Suivi
- ✅ Pattern bien rodé Supabase Auth, support natif
- ⚠️ Workflow admin-create plus complexe que self-signup, nécessite interface `/sourcing/admin/users`
- ⚠️ Le mot de passe provisoire transite en clair par email — c'est intrinsèque au pattern, mitigation par expiration courte (24h, cf. ADR-010)

### Alternatives rejetées
- **Magic-link Supabase** : bloqué par le scanner email AlyoS, démontré en pratique
- **OTP code 6 chiffres** : moins familier pour les users AlyoS habitués à edifio Suivi (email+password), supplémentaire à apprendre
- **SSO Edifio** : non implémenté côté plateforme Edifio, complexité hors scope MVP
- **OAuth Google Workspace AlyoS** : exigerait un déploiement IT AlyoS, hors scope MVP

## ADR-008 — Projet Vercel sous compte personnel TEISSIER (temporaire)

**Statut** : Acté de facto, à reverser
**Date** : 2026-05-10

### Contexte
Lors du setup Vercel par le Board, le projet `edifio-sourcing` a été créé sous le compte Vercel personnel de TEISSIER (`teissiers-projects.vercel.app`) au lieu d'une organisation d'équipe AlyoSIng.

### Décision provisoire
**On accepte la situation pour le MVP** (rapidité de mise en route). Action ouverte : migrer vers une **org Vercel AlyoSIng** avant Gate 9 (production).

### Conséquences
- ✅ Aucun blocage technique immédiat — Vercel fonctionne pareil sur compte perso ou org
- ⚠️ Continuité de service compromise si TEISSIER s'absente ou perd l'accès → blocage total déploiement
- ⚠️ Pas de partage facile des accès admin avec d'autres collaborateurs AlyoS
- ⚠️ Facturation Vercel rattachée au compte perso (pas comptabilité AlyoS)

### Plan de migration (avant Gate 9)
1. Créer une **org Vercel** sous le nom `AlyoSIng` ou `alyos-ingenierie` (compte payant Team ~20 €/user/mois — déjà budgétisé dans `budget_infra_v1.md`)
2. Inviter TEISSIER comme owner + Léa/Sophie comme admin
3. **Transfer Project** : Settings → Transfer Project → cible l'org AlyoSIng
4. Vérifier que les env vars, domain configs, et CI/CD continuent de fonctionner
5. Mettre à jour les URLs preview dans `DECISIONS.md` et la spec Supabase Auth Redirect URLs

### Alternatives rejetées
- **Rester sous compte perso indéfiniment** : risque de continuité inacceptable
- **Migrer maintenant** : ajout de friction sur un setup déjà chargé, à faire quand tout est stabilisé

## ADR-009 — Domaine email de transactional via Resend sur `alyosingenierie.fr`

**Statut** : Acté Board 2026-05-10
**Date** : 2026-05-10

### Contexte
edifio Sourcing envoie deux catégories d'emails :
1. **Transactionnels architectes** (sollicitation, relance, diffusion dossier) — déjà budgétisés via Brevo
2. **Transactionnels utilisateurs AlyoS** (mot de passe provisoire, reset password, récap Solo) — via Resend

Il fallait choisir le domaine émetteur des emails Resend.

### Décision
**Utiliser le domaine `alyosingenierie.fr` directement** (pas de sous-domaine dédié type `notif.alyosingenierie.fr`).

Aliases d'envoi recommandés :
- `noreply@alyosingenierie.fr` — envois système automatiques
- `contact@alyosingenierie.fr` — envois nominaux où le destinataire peut répondre
- `dpo@alyosingenierie.fr` — pour les communications RGPD (à activer Gate 9)

DNS records ajoutés chez OVH :
- TXT `resend._domainkey` (DKIM, valeur fournie par Resend)
- TXT `send` (SPF `v=spf1 include:amazonses.com ~all`)
- MX `send` (`feedback-smtp.eu-west-1.amazonses.com` priorité 10)
- TXT `_dmarc` (`v=DMARC1; p=none;` mode monitoring initial)

### Conséquences
- ✅ Les emails partent depuis le domaine principal AlyoS, image cohérente
- ✅ Mêmes records SPF/DKIM/DMARC peuvent être utilisés pour Brevo (à confirmer côté Brevo)
- ⚠️ Si réputation domaine `alyosingenierie.fr` est endommagée (spam, plaintes), impact sur TOUT le mail AlyoS
- ⚠️ Mitigation : DMARC en `p=none` au démarrage (mode observation), durcissement progressif vers `p=quarantine` puis `p=reject` après 3 mois

### Alternatives rejetées
- **Sous-domaine dédié `notif.alyosingenierie.fr`** : meilleure isolation de réputation, mais friction utilisateur (les emails ne ressemblent pas à de l'AlyoS)
- **Domaine Resend par défaut** : moins de confiance vis-à-vis des récepteurs, plus de spam, friction de configuration

## ADR-010 — 4 paramètres de sécurité auth (Q1-Q4 Board)

**Statut** : Acté Board 2026-05-10
**Date** : 2026-05-10

### Contexte
Au cours du pivot auth password (ADR-007), 4 paramètres restaient à arbitrer :
1. Durée d'expiration du mot de passe provisoire
2. Règles de complexité du mot de passe définitif
3. MFA obligatoire pour les admins
4. Rate-limit en cas d'échec de login

### Décision Board

| # | Paramètre | Valeur actée |
|---|-----------|--------------|
| Q1 | Expiration provisoire | **24 heures** (option B, surclasse reco CTO 7 jours) |
| Q2 | Complexité password | **16 car. min + 1 maj + 1 min + 1 chiffre + 1 symbole** (option B, surclasse reco CTO 12 car.) |
| Q3 | MFA admin | **Optionnel au MVP** (option A, reco CTO+CEO suivie) |
| Q4 | Rate-limit | **5 tentatives / 15 min puis blocage** (option A, default Supabase) |

### Conséquences
- ✅ Posture sécurité forte assumée pour un outil interne sensible (Q1 + Q2)
- ✅ MFA optionnel évite friction MVP, activable selon usage (Q3)
- ✅ Rate-limit standard équilibre sécurité et UX (Q4)
- ⚠️ Le 24h Q1 peut frustrer un user en congé/weekend → mitigation : l'admin peut régénérer un nouveau mot de passe provisoire en un clic (bouton « Renvoyer » en M14)
- ⚠️ Le 16 caractères Q2 peut frustrer les users qui aiment les mots de passe courts → mitigation : UI encourage activement les passphrases avec exemple visible (« montagne bleue sourire café 7 ! »)

### Métriques de suivi
- Taux de re-générations de mot de passe provisoire pendant les 4 premières semaines (target : < 30 %)
- Temps moyen entre invitation et première connexion (target : < 12 h en moyenne)
- Taux d'utilisateurs activant le MFA volontairement à 90 jours (target : > 50 % pour les rôles admin)

### Alternatives rejetées
- Détail dans `DECISIONS.md` § 2026-05-10 § Paramètres auth password détaillés
