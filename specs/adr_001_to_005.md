## ADR-001 — Stack web : Next.js 14 App Router + TypeScript + Tailwind + shadcn/ui hybride

**Statut** : Acté Gate 5
**Date** : 2026-05-07

### Contexte
Le brief Board v1.0 impose Next.js 14, TypeScript, Tailwind, shadcn/ui. Le seul point à arbitrer : shadcn/ui pur vs composants custom Edifio vs hybride.

### Décision
**Hybride** :
- shadcn/ui pour les primitives universelles (`Button`, `Input`, `Dialog`, `Select`, `Tabs`, `Toast`, `Tooltip`), thématisées via les CSS variables issues de `design/tokens.json`.
- Composants custom Edifio pour les patterns métier : carte AO, kanban-card, side-by-side IA, page tokenisée architecte.

### Conséquences
- ✅ Effort initial faible (~2 sem vs 4-6 sem en custom from scratch)
- ✅ Accessibilité Radix UI native (RGAA AA facilité)
- ✅ Design system Edifio préservé via tokens
- ⚠️ Dépendance shadcn/ui : si upstream breaking change, refactor possible — atténué car shadcn est *copié* dans le repo (pas un package installé)
- ⚠️ Discipline requise : ne pas mixer styles tailwind ad-hoc et tokens — toujours passer par les CSS variables

### Alternatives rejetées
- **shadcn/ui pur** : pas assez expressif pour les composants métier complexes (kanban, side-by-side IA)
- **Custom from scratch** : effort prohibitif (4-6 sem), retarde Gate 6
- **Material UI / Mantine** : design opposé au DS Edifio, refactor lourd pour thématiser

## ADR-002 — Multi-tenancy : RLS Postgres FORCE + isolation par `organization_id`

**Statut** : Acté Gate 5
**Date** : 2026-05-07

### Contexte
Le brief Board v1.0 acte un SaaS multi-tenant. Le pivot Board du 2026-05-10 ramène l'usage à 1 seul tenant (AlyoS) au MVP. Quid de l'effort multi-tenant J0 ?

### Décision
**Conserver le schéma multi-tenant complet dès J0**. Toutes les tables portent `organization_id`, RLS FORCE activée, politiques `tenant_isolation` sur 100 % des tables. Une seule organisation au démarrage : AlyoS.

### Conséquences
- ✅ Pas de dette technique pour la Phase 2 (ouverture multi-clients)
- ✅ Tests pgTAP cross-tenant exécutés dès Gate 6 (même avec une seule org)
- ✅ Helper `current_organization_id()` factorisé dans le schéma
- ⚠️ Surcoût léger sur les requêtes (RLS check à chaque scan) — négligeable sur volumes MVP

### Alternatives rejetées
- **Tables sans `organization_id` pour le MVP, refacto Phase 2** : dette technique majeure, risque de fuite cross-tenant lors de l'ouverture
- **Schémas Postgres séparés par tenant** : complexité de migration, pas d'intérêt à 1 tenant

## ADR-003 — Worker scraping : Vercel + Edge Functions Supabase + container Fly.io EU

**Statut** : Acté Gate 5
**Date** : 2026-05-07

### Contexte
4 plateformes à sourcer : BOAMP (API), PLACE (scraping authentifié), Francmarchés (scraping), MP.info (scraping). Sessions Playwright = 30-90 s par run. Cron quotidien à HH:MM Europe/Paris.

### Décision
**Architecture hybride** :
- BOAMP (API ouverte) : Vercel Cron déclenche une Edge Function Supabase qui appelle l'API
- Playwright (Francmarchés, MP.info, PLACE) : **container dédié Fly.io EU** (Frankfurt), déclenché par message Supabase Realtime depuis l'orchestrateur Edge Function

### Conséquences
- ✅ Pas de limitation 60 s Vercel Pro qui pénalise Playwright
- ✅ Coût ~5 €/mois sur Fly.io 256 Mo (dans le budget infra-only)
- ✅ Navigateur warm conservé entre les jobs (gain de latence)
- ⚠️ Composant supplémentaire à monitorer (Fly.io statut + logs)
- ⚠️ Communication Edge Function ↔ container via message bus Supabase Realtime — bien tester

### Alternatives rejetées
- **Vercel Functions Pro 60 s** : insuffisant pour Playwright
- **Vercel Enterprise 300 s** : +500 €/mois, hors budget
- **Self-hosted serveur OVH** : surcoût de gestion (sécurité, mises à jour, certificats)

## ADR-004 — Adaptateur Odoo : couche unique avec détection auto de version (17/18/19)

**Statut** : Acté Gate 5
**Date** : 2026-05-07

### Contexte
Compatibilité Odoo 17, 18, 19 demandée par le brief. Faut-il un adapter unique avec branchements internes, ou des adapters séparés par version ?

### Décision
**Couche unique** : interface `OdooAdapter`, implémentation `OdooXmlRpcAdapter` avec détection de version au handshake initial. Branchements internes minimaux pour les divergences de champs custom uniquement.

```ts
interface OdooAdapter {
  detectVersion(): Promise<17 | 18 | 19>
  createOpportunity(data: TenderToOpportunity): Promise<OpportunityId>
  updateStage(id: OpportunityId, stage: Stage): Promise<void>
  syncStatus(): Promise<SyncReport>
}
```

### Conséquences
- ✅ Maintenance simplifiée (un seul fichier à maintenir)
- ✅ XML-RPC est stable depuis 15 ans — peu de divergences entre versions
- ⚠️ Si Odoo 20 casse l'API, refactor à ce moment

### Alternatives rejetées
- **Adapters séparés par version** : trois fichiers à maintenir pour des divergences mineures
- **Librairie tierce** (`@flectra-hq/odoo-jsonrpc` etc.) : ajout de dépendance inutile, XML-RPC tient en < 200 lignes

## ADR-005 — Self-host fonts (Inter / Space Grotesk / JetBrains Mono)

**Statut** : Acté Gate 5
**Date** : 2026-05-07

### Contexte
Le DS Edifio repose sur 3 fonts Google Fonts. Servir depuis `fonts.googleapis.com` est le défaut Next.js. Mais 3 contraintes s'opposent : PWA offline, RGPD (IP visiteur transmise à Google), performance LCP.

### Décision
**Auto-hébergement obligatoire**. Téléchargement WOFF2 depuis `fontsource.org` au build, servies depuis `/public/fonts/` avec `Cache-Control: public, max-age=31536000, immutable` et `font-display: swap`. **Aucun appel à `fonts.googleapis.com`** ni à `fonts.gstatic.com`.

### Conséquences
- ✅ PWA offline fonctionne (fonts dans le SW cache)
- ✅ Conformité RGPD (pas de fuite IP vers Google)
- ✅ Performance LCP améliorée (pas de DNS / connect / TLS handshake supplémentaire)
- ⚠️ Mises à jour des fonts à pinner manuellement (upgrade `fontsource` à la main si version majeure)

### Alternatives rejetées
- **Google Fonts CDN par défaut** : violation RGPD + dégradation LCP
- **Service-worker proxy** : complexité injustifiée
