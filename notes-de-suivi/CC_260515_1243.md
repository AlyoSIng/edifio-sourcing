## 1. TL;DR

- Sourcing = pipeline cron quotidien BOAMP + 3 scrapers Fly.io, **insert/upsert lourd** sur `tenders` avec contrainte d'idempotence `(organization_id, external_ref, platform_id)`.
- Le **point chaud ORM** n'est pas la requête utilisateur mais le **batch d'upsert + JSON `raw_data` + RLS** exécuté côté **Supabase Edge Function (Deno)** — donc cold start ET compat Deno comptent autant l'un que l'autre.
- 22+ tables, RLS FORCE 100 %, **9 colonnes jsonb**, 1 trigger d'immutabilité (`audit_logs`), 4 colonnes `text[]`, 1 extension `pg_trgm` pour full-text fuzzy sur `tenders.title`.
- Schéma `specs/schema_v1.sql` figé Gate 5 → conversion 1:1 attendue (drizzle-kit introspect OU prisma db pull). Pas de modélisation à inventer pendant le spike.

## 3. Volumétries et patterns d'écriture

- **Cron Vercel** : `30 6 * * 1-5`, 5 j/semaine. Déclenche un fan-out par `search_profile` actif → Edge Function orchestrator.
- **Inputs bruts** : 1100-3300 AO/jour cumulés sur les 4 plateformes. Après dédup + filtre profil : 5-30 retenus/profil/jour.
- **Pattern d'écriture chaud** : `upsert tenders` avec `onConflict: (organization_id, external_ref, platform_id)` + JSON `raw_data` non négligeable (record Opendatasoft entier). Cadence : 1100-3300 upserts en ~10 min cible (k6 Gate 9).
- **Écritures secondaires par run** : `tender_events` (audit natif), `audit_logs` (action `ai_run` si scoring IA), `notifications` (Realtime push).
- **Updates fréquents** sur `tenders.status` (14 transitions), `tenders.score` (re-scoring possible), `architect_tokens.revoked`.

## 4. Patterns de lecture chauds

1. **Kanban Solo/Tandem** : `SELECT FROM tenders WHERE organization_id=? AND status IN (...) ORDER BY score DESC` → index `idx_tenders_org_status` + `idx_tenders_score`.
2. **AO du jour** : `WHERE deadline > now()` → index partiel `idx_tenders_deadline`.
3. **Recherche fuzzy titre** : `pg_trgm` GIN sur `tenders.title` (`idx_tenders_title_trgm`). **L'ORM doit savoir émettre du SQL trigram natif** (probablement raw fragment).
4. **Matching architectes** : `architects.specialty_codes` (text[]) intersect avec besoin AO → index GIN.
5. **Lookup token architecte** : `WHERE jwt_id=? AND revoked=FALSE` → index partiel.
6. **Pas de pgvector** dans le schéma v1 (sémantique reportée Phase 2 ML via `learning_events`).

## 5. RLS et multi-tenancy

- 20 tables avec RLS ENABLE, 19 avec **FORCE** (interdit le bypass `service_role` côté app).
- Politique standard : `organization_id = current_organization_id()` (helper qui lit `request.jwt.claims -> app_metadata -> organization_id`).
- **Cas plus complexes** : `tender_lots` (sous-requête EXISTS sur `tenders`), `notifications` (double filtre `org + user_id = auth.jwt()->>'sub'`), `audit_logs` (filtre admin via `current_user_role()`).
- Impact perf prévisible : la sous-requête `tender_lots` est la seule à risque, le reste reste sargable.
- Le helper `current_organization_id()` est `STABLE` → planner-friendly. **Les Edge Functions doivent propager le JWT utilisateur**, pas utiliser service_role, sinon RLS bypass = veto sécurité.

## 6. Edge Functions / cron / Realtime

- **Cold start critique** : 1 Vercel API Route (`/api/cron/sourcing-run`) + 1 Supabase Edge Function Deno (`sourcing-orchestrator`) + 1 webhook Vercel (`/api/webhooks/scraper-done`). Le pipeline complet doit boucler **< 10 min sur 1000 AO** (k6 Gate 9).
- **Compat Deno requise** : `sourcing-orchestrator` tourne sur Supabase Edge (V8/Deno isolates). Prisma sur Deno = supabase-js + driver adapter ou Data Proxy. Drizzle = compat native via postgres-js/HTTP. **Critère décisif.**
- **Realtime** : push `notifications` post-sourcing (abonnement par user). Pas géré par l'ORM, mais l'INSERT déclencheur l'est.
- **Storage** : `tender_documents.storage_path` pointe Supabase Storage. Pas de blob en BDD.

## 7. Pondération Gate 5 à la lumière de la spec

Pondération actée Board : **cold start 50 % · DX 25 % · Supabase+RLS 15 % · maturité 10 %**.

À la lecture, deux signaux pourraient déplacer marginalement le curseur (à confirmer Board, pas une proposition de ma part) :
- Le pipeline d'écriture **vit majoritairement dans Edge Function Deno**, ce qui rend la **compat Supabase+RLS+Deno** plus structurante que les 15 % nominaux ne le laissent penser. Si on lit "Supabase+RLS" comme englobant la compat runtime Deno, c'est cohérent ; sinon ça mérite clarification.
- **9 colonnes jsonb et 6 enums Postgres** : la qualité du typage TS côté ORM (jsonb typé via Zod, enum natif vs string) est entièrement dans les 25 % DX — donc la pondération existante couvre déjà ce point.

## 8. Risques / inconnues à clarifier AVANT spike

1. **Format `tenders.raw_data`** : taille moyenne ? La spec dit "payload brut Opendatasoft" sans cap. Si > 50 KB en moyenne, l'upsert devient bandwidth-bound, pas ORM-bound.
2. **Nombre exact de policies RLS à porter** : le schéma définit `tenant_isolation` USING (lecture) mais **les WITH CHECK INSERT/UPDATE sont volontairement minimaux** (commentaire L553 : "Alex complétera"). À chiffrer pour estimer l'effort migrations côté chaque ORM.
3. **Supabase Edge Function en Deno : runtime ORM autorisé ?** Drizzle a un driver postgres-js Deno-compatible, Prisma exige Data Proxy ou driver-adapter. **À tester explicitement dans le spike, pas après.**
4. **Trigger d'immutabilité `audit_logs`** + **trigger `touch_updated_at` sur 5 tables** : doivent être gérés en migration "raw SQL" hors ORM. Confirmer que les deux outils le supportent proprement dans leur dossier de migrations.
5. **Scoring complémentaire IA** : la spec mentionne `Tier >= Cotraitance` (notion tarifaire) qui n'est pas dans le schéma v1. À confirmer : pas de table `tiers` à modéliser dans le spike.
