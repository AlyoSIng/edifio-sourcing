## 1. Diff staged — correctif S4 recovery durable

### Symptôme observé

Le flow « mot de passe oublié » d'un user durable arrivait sur `/reset-password`
avec le bandeau « Lien invalide ou expiré » alors que le lien était valide.

### Cause racine

Supabase Auth en mode implicit flow renvoie les tokens recovery dans le
**fragment d'URL** (`#access_token=…`). Seul le browser peut le lire ; côté
serveur Next.js, `/reset-password` ne voyait aucune session établie → tombait
dans `InvalidStateBlock`.

Le `requestPasswordResetAction` posait `redirectTo = /reset-password` direct,
sans passer par `/auth/callback` qui sait décoder le fragment via le
`ClientCallbackHandler` côté browser et établir la session.

### Correctif (5 fichiers, +66 / −25)

| Fichier | Changement |
|---|---|
| `src/app/forgot-password/actions.ts` | `redirectTo = ${getSiteUrl()}/auth/callback?next=/reset-password` |
| `src/app/reset-password/page.tsx` | 3 modes au lieu de 2 : cas (3) « session fraîche posée par callback » accepté en mode recovery |
| `src/app/reset-password/actions.ts` | Snapshot `wasFirstLogin = currentMeta.must_change_password === true` AVANT update — distingue first-login / recovery sans dépendre de `code` (cas 3 arrive sans code) |
| `src/app/login/actions.ts` | Si `mustChangePassword(profile)` → `redirectTo = "/reset-password"` direct (court-circuite la dépendance au middleware, élimine la latence cookie observée en CI) |
| `e2e/auth-password.spec.ts` | S4 utilise `${baseURL}/auth/callback?next=/reset-password` au lieu de `${baseURL}/reset-password` |

Les commentaires JSDoc d'en-tête de `reset-password/page.tsx` (lignes 13-25) et
`reset-password/actions.ts` (lignes 11-28) parlent encore de « Deux contextes »
/ « Deux flows ». Les commentaires *internes* dans la fonction sont à jour
(3 cas, `wasFirstLogin`). Désync mineure documentaire — je propose à Yann de
les aligner dans le bundle commit pour éviter de laisser un faux indice à un
relecteur futur.

  de la PR, sur le même projet Supabase, dans un environnement isolé.

**Conclusion** : valider via la CI à l'ouverture PR. Si la CI échoue sur S4,
l'erreur sera explicitement « redirect URL not allowed » → on saura quoi
ajouter au panel Supabase Dashboard.

## 2. Constat DNS Resend — bloquant pour envoi bout-en-bout

### Annonce Board reçue ce matin

Le Board a configuré chez OVH les records DKIM + SPF + MX + DMARC pour
`alyosingenierie.fr`, propagation supposée en cours.

### Lookups effectués (résolveur Google `8.8.8.8` puis NS faisant autorité)

| Record | Présent ? | Détail |
|---|---|---|
| NS `alyosingenierie.fr` | ⚠️ | `ns1016.ui-dns.com/.de/.biz/.org` → **IONOS, pas OVH** |
| TXT `resend._domainkey` | ❌ | Inexistant chez Google ET chez IONOS faisant autorité |
| TXT `_dmarc` | ❌ | Inexistant |
| TXT racine SPF | ⚠️ | `v=spf1 include:spf.protection.outlook.com -all` — Outlook seul, **Resend bloqué par le `-all`** |
| MX `alyosingenierie.fr` | ✅ | `alyosingenierie-fr.mail.protection.outlook.com` (inchangé) |
| TXT `MS=ms82624951` | ✅ | Vérification Microsoft 365 (inchangé) |
| Sous-domaine `send.alyosingenierie.fr` | ❌ | Zone entière inexistante |

### Diagnostic

Ce n'est **pas un délai de propagation**. La zone DNS qui sert réellement
le domaine est chez **IONOS**, pas OVH. Les records Resend posés dans le
panel OVH (si c'est bien là qu'ils ont été posés) ne sortiront jamais
parce que les résolveurs interrogent IONOS qui n'a rien à servir.

### Deux options de remédiation (proposées au Board)

- **Option A — reposer la config chez IONOS** (recommandée par Alex) :
  ajouter dans le panel IONOS les 3 records Resend. Stratégie sous-domaine
  `send.alyosingenierie.fr` recommandée par Resend quand un SPF Outlook
  existe déjà (pas de modification du SPF racine → zéro risque pour les
  mails Outlook actuels). Propagation IONOS : 5-30 min en pratique.
- **Option B — basculer la délégation DNS chez OVH** : nécessite de migrer
  d'abord tous les records actuels (SPF Outlook, MX, `MS=…`) sous peine de
  casser la messagerie AlyoS. Pas justifié pour ce besoin.

### Impact côté code

- Le code `forgot-password` + `welcome_provisional_password` est fonctionnellement
  prêt et appelle Resend correctement (cf. `src/lib/email/send.ts`).
- Tant que Resend ne montre pas « Domain Verified », `sendPasswordResetEmail`
  et `sendWelcomeProvisionalPassword` échoueront avec une erreur Resend (loguée
  côté serveur, transparente côté UI grâce à l'anti-énumération du flow
  forgot-password — succès apparent même si l'email n'est pas envoyé).
- Le scénario S4 E2E **ne dépend PAS de Resend** (utilise `admin.generateLink`
  directement). Donc la CI peut valider le correctif S4 indépendamment du DNS.
- Le test bout-en-bout « user reçoit vraiment l'email recovery dans son inbox »
  reste bloqué tant que Domain Verified Resend n'est pas atteint.

1. **Préférer Option A pour le DNS** plutôt que tout migrer vers OVH.
   Justification : moins risqué (zéro changement pour Outlook) et plus rapide.
2. **Stratégie sous-domaine `send.alyosingenierie.fr`** plutôt qu'amendement
   du SPF racine. Justification : Resend recommande explicitement ce pattern

   signal/risque défavorable (cf. §1).
