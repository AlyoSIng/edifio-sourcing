## 2. Bug `error_code=otp_expired` — scanner email AlyoS

### Symptôme

Après correction du double-https : URL arrive sur la racine `/` avec un
fragment d'erreur `#error=access_denied&error_code=otp_expired&error_description=…`.
Aucune indication UI : l'utilisateur voit la landing page edifio normale.

### Cause racine

Le scanner email entreprise AlyoS (Microsoft Defender Safe Links / équivalent
Outlook 365) **pré-clique automatiquement les liens recovery dès réception
du mail** pour vérification sécurité. Le pré-clic consume le token Supabase
one-time → le clic réel du user arrive sur un token déjà invalidé.

### Anomalie subsidiaire Supabase

Quand le token est consommé, Supabase **ignore systématiquement notre
`redirect_to`** (`/auth/callback?next=…`) et fait fallback sur le **Site URL
Dashboard** avec le fragment d'erreur. Comportement non documenté
explicitement. Le user atterrit donc sur la racine `/` au lieu de
`/auth/callback`.

### Décision Board — ADR-011

Cf. `specs/adr_011_reset_password_scanner.md`.

**Option 1 immédiate** (livrée cette session) :
- Page `/auth/error` avec messages FR par `error_code` + CTA `/forgot-password`
- `HashErrorHandler` Client Component qui intercepte le fragment d'erreur
  sur la home `/` et redirige vers `/auth/error?code=…`
- `ClientCallbackHandler` étendu pour traiter aussi le fragment d'erreur
- `auth/callback/page.tsx` redirige `?error=…` vers `/auth/error` (au lieu
  de `/login?error=…`)

**Option 2 planifiée** (Gate 6 étape 6, P1) :
- OTP 6 chiffres par email (sans clic) — résout 100 % du problème scanner.
- Coexiste avec le flow lien existant.

**Option 3 rejetée** :
- Resend custom link → ne résout pas le scanner (pré-clique TOUT lien).

## 6. Décisions ad hoc prises en autonomie

1. **Page `/auth/error` route publique** (pas de garde middleware) parce
   que l'utilisateur arrive en erreur sans session active. Cohérent avec
   `/login`, `/forgot-password`, `/reset-password`.
2. **`HashErrorHandler` attaché à la home uniquement**, pas au layout
   racine, pour ne pas interférer avec `/auth/callback` qui a son propre
   handler ni `/reset-password` qui peut recevoir un fragment d'access_token
   dans le cas 3 (recovery via session fraîche posée par callback).
3. **`console.warn` (et pas `console.error`) dans `normalizeSiteUrl`** —
   c'est de la défense en profondeur, pas une erreur fatale. Le warning
   apparaît dans les logs Vercel pour signaler la config foireuse à l'admin
   sans faire planter l'app.
4. **`redirect_to` Supabase reste `/auth/callback?next=/reset-password`**
   malgré le comportement de fallback Site URL observé. Inutile de
   contourner — la couverture `HashErrorHandler` + `/auth/error` couvre
   les deux chemins (callback OU racine).
